# Internationalization (i18n)

The web UI ships in **English (`en`, default)** and **Vietnamese (`vi`)** using
[next-intl](https://next-intl.dev) with no locale prefix in URLs. Epic: KAN-220 (UI only).

## How the locale is chosen

Per request, in this order (`src/lib/i18n/resolve-locale.ts`, wired in `src/lib/i18n/request.ts`):

1. the `NEXT_LOCALE` cookie, written by the language switcher (one year, `SameSite=Lax`);
2. the browser's `Accept-Language` header (`vi`, `vi-VN` → `vi`);
3. English.

Because the locale is read from the request, pages render on demand instead of being built as static HTML.

`<html lang>` follows the active locale in `src/app/layout.tsx` and `src/app/global-error.tsx`
(the error boundary replaces the root layout, so it resolves the locale itself).

The switcher (`src/components/layout/language-switcher.tsx`) is in the public headers, the auth
pages and the workspace header for every role. It saves the cookie and calls `router.refresh()`,
so the page re-renders in place and form input is kept. **It is never shown in the interview room.**

Adding a locale starts in `src/lib/i18n/config.ts` (`locales`, `localeNames`), then a folder under
`src/lib/i18n/messages/<locale>/` and an entry in `formatters.ts` (`intlLocales`).

## What stays English

- The interview: interviewer speech (TTS), voice profiles, STT, question-bank generation, follow-ups,
  evaluation feedback and scores. The room has no switcher and `src/features/interview/**` is not translated.
- User- or AI-generated content: JD text, extracted requirements, core questions, transcripts, CVs,
  evaluation feedback. Render it as stored.
- Backend error `message` text and Better Auth `message` text. Show a translation chosen by **code**, never the raw text.
- Log lines, test ids, route paths, API field names.

## Catalogs and who edits what

Catalogs live in `src/lib/i18n/messages/{en,vi}/`, one JSON file per area. The top-level key is the
namespace you pass to `useTranslations`.

| File              | Namespace    | Owner / use                                                                 |
| ----------------- | ------------ | --------------------------------------------------------------------------- |
| `common.json`     | `common`     | Foundation: shared words, switcher, global error, `common.format.*`         |
| `errors.json`     | `errors`     | Foundation: API error codes (`errors.api.*`), Better Auth (`errors.auth.*`) |
| `validation.json` | `validation` | Foundation: reusable form-validation messages                               |
| `public.json`     | `public`     | Landing, pricing, privacy, terms, public header                             |
| `auth.json`       | `auth`       | Login, register, recovery, 2FA, account security screens                    |
| `candidate.json`  | `candidate`  | Candidate screens                                                           |
| `recruiter.json`  | `recruiter`  | Recruiter screens                                                           |
| `admin.json`      | `admin`      | Admin screens                                                               |

Rules that keep parallel translators conflict-free:

- **One area, one file.** Translate a screen by adding keys only to the file of its area. Do not
  reorganise another area's file or the `index.ts` files.
- **Nest by screen, then by element**: `recruiter.postings.list.emptyTitle`. Name keys by meaning, not
  by the English text (`submit`, not `saveChanges2`).
- **English and Vietnamese change together.** Every key exists in both files. A parity test
  (`tests/unit/lib/i18n/catalog.test.ts`) fails when one side is missing.
- Shared words used by several areas (Cancel, Save, Retry…) go in `common` once; reuse, don't copy.
- A key missing in `vi` falls back to English and is logged in development
  (`[i18n] N message key(s) missing in "vi"…`), so a half-translated screen never crashes.
- Keys are typed (`src/lib/i18n/next-intl.d.ts`): a typo in a namespace or key fails `bun run typecheck`.

## Adding a string

```json
// messages/en/recruiter.json                 // messages/vi/recruiter.json
{ "postings": { "list": {                    { "postings": { "list": {
    "emptyTitle": "No postings yet" } } }        "emptyTitle": "Chưa có tin tuyển dụng nào" } } }
```

Client Component:

```tsx
const t = useTranslations("recruiter.postings.list");
return <h2>{t("emptyTitle")}</h2>;
```

Server Component (async): `const t = await getTranslations("recruiter.postings.list");`.

Use ICU for values and plurals, never string concatenation:

```json
{ "questionCount": "{count, plural, one {# question} other {# questions}}" }
```

Vietnamese has no plural forms; write `"{count} câu hỏi"` (or `{count, plural, other {# câu hỏi}}`).

Vietnamese copy must read naturally, not word-for-word. Agreed vocabulary: _coin_ → **xu**,
_job posting_ → **tin tuyển dụng**, _interview slot_ → **lượt phỏng vấn**, _role profile_ →
**hồ sơ vị trí**, _you_ → **bạn**.

## Formatting dates, numbers, coins and VND (KAN-223)

Never call `toLocale*`, `Intl.*`, date-fns or dayjs in a feature. ESLint rejects `Intl.*` and
`toLocale*` outside `src/lib/i18n`. Use the formatters (`src/lib/i18n/formatters.ts`):

```tsx
const fmt = useFormatters(); // Client; Server: const fmt = await getFormatters();
fmt.date(post.created_at, "calendarDay"); // Oct 12, 2026 / 12 thg 10, 2026
fmt.date(deadline, "moment"); // viewer's time zone, zone named
fmt.relative(startedAt); // 5 minutes ago / 5 phút trước
fmt.timeLeft(deadline, now); // 3 h 20 min left / Còn 3 giờ 20 phút
fmt.number(1234.5); // 1,234.5 / 1.234,5
fmt.percent(12.5); // 12.5% / 12,5%
fmt.coinAmount(1500); // 1,500 / 1.500   (no unit)
fmt.coins(1500); // 1,500 coins / 1.500 xu   (unit + plural)
fmt.vnd(100000); // 100.000 ₫  (same in both languages)
fmt.list(["Google", "GitHub"], "disjunction");
```

Plain functions (utils) take the formatters as a parameter (`formatDeadline(iso, fmt)`) or the pure
versions (`formatDate(value, locale, style)`, `formatNumber(value, locale)`, `formatVnd(amount)`).

Rules:

- **Format only, never convert.** Amounts and dates come from the API unchanged. VND is not converted to
  other currencies; coins are not rescaled.
- **Time zones.** `calendarDay`, `calendarDayTime` and `monthYear` use UTC because the value is a
  calendar day or a stored instant. `moment`, `momentPadded`, `localDateTime`, `dayMonthYear` and
  `transaction` use the viewer's own zone. Pick the style that matches the old behaviour; do not
  switch a UTC day to local.
- **Coin counts group like any number** in the active locale (`1,500` / `1.500`), including on admin billing.
- **VND keeps Vietnamese conventions in every language** (`100.000 ₫`), as the payment provider and bank
  show it. Admin finance reports also stay `dd/MM/yyyy HH:mm` in Vietnam time (`vietnamDateTime`).
- An unreadable date renders as an empty string; callers that want a placeholder write `fmt.date(x) || "—"`.
- The 24-hour `interview_deadline` countdown is `fmt.timeLeft`; copy lives in `common.format.timeLeft.*`.
- Need a new date shape? Add a named style to `dateStyles` with a test in `formatters.test.ts` rather
  than inline options.

## API errors (KAN-224)

The backend keeps responses locale-independent: `{ success:false, error:{ code, message } }`. The UI
maps the stable `code` to text in the active language. Codes are defined in
`api/pkg/apperror/apperr.go`; a test fails when a Go code has no entry in `errors.api`.

```tsx
const errorMessage = useApiErrorMessage(); // or apiErrorMessage(t, error, fallback)
<p role="alert">{errorMessage(mutation.error, t("saveFailed"))}</p>;
```

Order: a code in `errors.api` → the screen's own translated `fallback` (used first for the
non-specific `INTERNAL_ERROR` and `VALIDATION_ERROR`) → "can't reach RoleCue" when offline → rate
limit → a generic translated line. **The server's `message` is never displayed.** Keep screen-specific
wording for a code in the screen's own namespace and fall through to `apiErrorMessage` for the rest
(see `capacityErrorMessage`, `applyErrorMessage`).

Adding a backend code: add it to `errors.json` in `en` and `vi` (the parity and Go-code tests tell you).

**Better Auth** errors are mapped by their `code` to `errors.auth.*`:
`getAuthErrorMessage(error, fallback, t)` for sign-in/up (wrong password, unverified email, locked
account) and `securityErrorMessage(error, t)` for account security and two-factor.
Pass `useTranslations("errors")` as `t`.

## Form validation (KAN-224)

Validation messages come from `validation.json`. Schemas are factories that take the translator, so a
field error is already in the active language:

```ts
export function createLoginSchema(v: Validation) {
  return z.object({
    email: z.string().min(1, v("emailRequired")).email(v("emailInvalid")),
  });
}
// in the component
const v = useTranslations("validation");
const schema = useMemo(() => createLoginSchema(v), [v]);
```

Reuse generic keys (`required`, `email`, `minLength`, `maxLength`) or add area-specific keys under
your own namespace. Auth and change-password schemas are the reference implementations. Schemas that still
contain English text (`moderation-schema`, `capacity-schema`, `question-bank-schema`, the recruiter and
admin schemas) are converted by the screen owners using this pattern.

## Testing

Helpers in `tests/helpers/intl.tsx`:

- `renderWithIntl(ui, { locale })` – render a component inside the provider (en by default).
- `formattersFor(locale)`, `errorsFor(locale)`, `validationFor(locale)` – the same translators/formatters
  a component gets, for testing plain functions.

English output of existing screens must not change when a screen is translated: keep the `en` text identical
and add a `vi` assertion for the new behaviour.
